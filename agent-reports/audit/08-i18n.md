## Findings

### [P1] 8.1 — The `<html lang>` attribute never reflects the negotiated locale

`getSiteLayoutContext()` (`siteLayoutContext.ts:7`) correctly computes `lang: getHtmlLang(locale)`, but `site/app/(site)/layout.tsx` destructures **only** `{ messages, locale }` — the `lang` field is discarded — and the root `site/app/layout.tsx:16` hardcodes `<html lang="en" …>`. Net effect: regardless of the `NEXT_LOCALE` cookie or `accept-language`, every page renders with `lang="en"`.

- A visitor who negotiated `hi`/`fr`/`de`/`es` gets `<html lang="en">` → screen readers announce the page in English-pronunciation rules for non-English content, and search engines see a document-language mismatch with the localized body copy (cross-ref 03-seo 3.3).
- Verified live: `results/audit/seo/full_root.html` shows `<html lang="en">` on the homepage.

**Evidence:** `site/app/layout.tsx:16`; `site/app/(site)/layout.tsx` (destructure drops `lang`); `site/lib/layout/siteLayoutContext.ts:7`; `results/audit/seo/full_root.html`.
**Owner action:** Pass the `lang` returned by `getSiteLayoutContext()` into the `<html lang>` — either set it in the root layout from the resolved locale, or restructure so the (site) layout controls `<html>`. **Fix 8.2 first**, otherwise wiring activates the fr/de/es mis-map.

### [P2] 8.2 — `htmlLang.ts` mis-maps `fr`/`de`/`es` to `*-IN` instead of `*-FR`/`*-DE`/`*-ES`

`HTML_LANG_BY_LOCALE` (`htmlLang.ts:5–10`) maps:

```
en → en-IN   (OK — English, India; defensible for an Indian company)
hi → hi-IN   (OK — Hindi, India)
fr → fr-IN   (WRONG — "French (India)" is a tiny union territory; standard is fr-FR)
de → de-IN   (WRONG — should be de-DE)
es → es-IN   (WRONG — should be es-ES)
```

This **contradicts** `LOCALE_HREFLANG` in `seo.ts` (which correctly maps `fr→fr-FR, de→de-DE, es→es-ES`). So the hreflang tags and the (intended) html `lang` would disagree for fr/de/es. Currently dormant because 8.1 never wires `lang` into `<html>`, but the moment 8.1 is fixed without fixing 8.2, fr/de/es pages declare `fr-IN`/`de-IN`/`es-IN` — both wrong and inconsistent with hreflang.

**Evidence:** `site/lib/i18n/htmlLang.ts:5–10`; `site/features/site/data/seo.ts:53–58` (`LOCALE_HREFLANG`).
**Owner action:** Change the three entries to `fr→fr-FR, de→de-DE, es→es-ES` (keep `en→en-IN, hi→hi-IN`); then wire `lang` (8.1).

### [P3] 8.3 — `LanguageSwitcher` cookie lacks the `Secure` flag

`handleChange` sets `document.cookie = "NEXT_LOCALE=${nextLocale}; path=/; max-age=31536000; SameSite=Lax"` — no `Secure`. Over HTTPS the cookie is still transported securely, but without `Secure` it could be sent over an accidental HTTP fetch. `SameSite=Lax` is appropriate for a locale preference (client-readable, non-sensitive). Low severity.

**Evidence:** `site/components/site/LanguageSwitcher.tsx` `handleChange`.
**Owner action:** Add `; Secure` when not in dev, or set the cookie server-side via `cookies().set` with `secure:process.env.NODE_ENV==="production"`.

### [P3] 8.4 — `localePrefix:"never"` makes hreflang self-referential only (no per-locale URL)

With `localePrefix:"never"` + cookie/header negotiation, every locale is served at the **same URL**. Verified on the homepage: all 6 `rel=alternate hrefLang` tags (`en-IN, hi-IN, fr-FR, de-DE, es-ES, x-default`) point to `https://oando.co.in/`. Google does not honor the `NEXT_LOCALE` cookie when crawling, so it cannot index localized content at distinct URLs — multilingual SEO is effectively single-locale from the crawler's view. This is a documented design tradeoff (the manifest treats hi as wave-1 parity and de/es/fr as deferred), not a bug, but it caps international SEO reach.

**Evidence:** `site/i18n/routing.ts` (`localePrefix:'never'`); `results/audit/seo/full_root.html` (6 hreflang → same origin).
**Owner action:** If distinct-locale indexing is desired later, switch `localePrefix` to `"as-needed"`/`"always"` (owner decision; affects all canonicals/redirects).
